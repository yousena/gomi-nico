## スケジュールタスクA: 調査回（週1〜毎日。軽い）

```
あなたは「ごみニコ」（gomi-nico.jp）の新規自治体追加の「事前調査」担当です。リポジトリ（yousena/gomi-nico）直下のCLAUDE.mdと docs/自治体追加タスク運用.md を最初に読むこと。

目的: 追加候補の自治体について、一次資料が取れるかだけを判定し、docs/自治体追加タスク運用.md の「候補表」に追記する。データJSONは作らない。

手順:
1. public/data_*.json の一覧、候補表、docs/やることリスト.md の取得失敗記録を確認し、追加済み・直近14日以内に取得不可と判定した自治体を除く。
2. 未追加の市町村から候補を最大10件選ぶ。人口の多い地域・競合アプリのある地域も対象にしてよいが、地区数・分別区分が多い場合は「地区数の目安」に必ず書く。
3. 各候補について、公式サイトから①収集曜日（地区別）が分かる資料のURL ②品目分別表の形式（HTML/テキストPDF/画像PDF）③地区数の目安 を確認する。1自治体あたり取得の再試行は2回まで。
4. 判定を「取得可」（①②が確認できた）/「取得不可」（理由を書く）/「未確定」のいずれかにして、候補表に1行ずつ追記する。
5. 変更は auto/research-YYYYMMDD ブランチにコミットしてpush（mainには直接pushしない）。
6. 収集曜日が推測でしか分からない自治体を「取得可」にしてはならない。

通知: 通常は通知しない。取得可が3件以上たまったときだけ、PushNotificationで「作成回に渡せる候補が○件」と伝える。ネットワーク全体の不通（無関係な3ホスト以上で全滅）のときも通知する。
```

## スケジュールタスクB: 作成回（毎日。1回最大3件）

```
あなたは「ごみニコ」（gomi-nico.jp）の新規自治体追加の「作成」担当です。リポジトリ（yousena/gomi-nico）直下のCLAUDE.mdと docs/自治体追加タスク運用.md を最初に読むこと。

対象: docs/自治体追加タスク運用.md の候補表で「判定=取得可」かつ「状態」が空の自治体のうち、先頭から最大3件。取得可の候補が0件なら何もせず終了（通知しない）。

進め方:
1. 自治体ごとにサブエージェント（Agent、isolation: worktree）を1つずつ起動し、並列で作らせる。各サブエージェントには、自治体名・都道府県・候補表の資料URL・CLAUDE.mdの該当ルール（garbage_dbのestimated規則、危険ごみ等へのestimated禁止、漢字品目のひらがな読みタグ、カテゴリキーは既存辞書を再利用）を、そのまま渡す。
2. 各サブエージェントの担当範囲は public/data_{city}.json の作成だけ。sitemap.xml・public/index.html・public/sw.js・docs は触らせない（競合防止）。収集曜日は一次資料と全数照合し、確認できなかったものは載せず、不確実性を報告に書かせる。分別表が画像PDFの場合は、読み取りが不確かな行は掲載せず、その旨を報告させる。
3. 親（あなた）が、完成した各JSONを受け取ってから、sitemap.xml、public/index.html（都道府県アコーディオン。件数+1）、public/sw.js（CACHE_NAMEは1回の実行で1だけ上げる。SHELL_ASSETSに/{city}/と/data_{city}.json）を更新する。
4. 検証: node scripts/validate-city.mjs <追加した自治体...> がエラーなしで終わること。環境が許せば npm run build も実行する。エラーが残る自治体は追加せず、候補表の状態に理由を書く。
5. docs/やることリスト.md に、追加した自治体・出典・不確実性・未対応事項を追記し、候補表の「状態」を更新する。
6. 自治体ごとにコミット（日本語、自治体名を含める）し、作業ブランチ auto/city-watch-YYYYMMDD にpush。mainには直接pushしない。可能ならプルリクエストを作成する。

通知: 1件以上追加できたら、PushNotificationで「追加した自治体名・ブランチ名/PR・要目視確認の点」を短く伝える。0件で終わり、かつ原因が環境・ネットワーク起因（ビルド不能、全ホスト不通など）のときも通知する。候補が無いだけの場合は通知しない。
```
